# World Repository and Creative Harness

Use this reference only when a durable repository or repository-specific harness materially helps the project.

## Select the operation

- **Memorialize:** Preserve creator source, establish attribution, and normalize it into a maintainable world structure.
- **Bootstrap:** Propose a provisional repository and harness before a repository exists.
- **Create:** Establish approved world structure or harness files in an existing repository.
- **Audit:** Report missing, duplicated, stale, or contradictory governance without writing.
- **Update:** Apply an approved targeted change and propagate its effects.
- **Repair:** Reconcile conflicting canon, provenance, instructions, or file routing.
- **Validate:** Check structure and governance without changing material.
- **Reconcile:** Align a provisional bootstrap package with the repository after creation.

## Establish authority and provenance

Record separately:

| Concern | Question |
|---|---|
| Original authorship | Who created the premise, source notes, characters, or setting? |
| Stewardship | Who is preserving, organizing, or maintaining the work now? |
| Source authority | Who resolves ambiguity in original material? |
| Canon authority | Who may accept, deprecate, or replace canon? |
| Editorial contribution | Which material is normalization, adaptation, collaboration, or AI-assisted proposal? |

Do not infer ownership transfer from repository maintenance. A claim needs a canon status and may also need provenance and an exact source reference.

## Preserve source material

1. Keep supplied originals in a clearly identified source area or external authoritative location.
2. Do not silently correct, modernize, or reorganize the preserved copy.
3. Normalize material into separate entries with source references.
4. Record alternatives, naming conflicts, and contradictions.
5. Preserve dated or sensitive material with context and a review requirement; preservation does not make it current canon.
6. Confirm confidentiality against repository visibility before any upload.

## Scale the repository

Use only applicable paths:

```text
README.md
AGENTS.md
bible/
characters/
locations/
stories/ or episodes/
history/ or mythology/
continuity/
source-material/
templates/
.github/
harness-manifest.yaml
```

Prefer modular files when characters, locations, stories, contributors, or changes will evolve independently. Prefer a smaller portable document when repository overhead would not improve continuity.

## Design the creative harness

Start with the smallest effective combination:

- root `AGENTS.md` for common governance and approval boundaries;
- nested instructions only for genuinely different subtree rules;
- `harness-manifest.yaml` for capability coverage and provisional assumptions;
- reusable entry and canon-decision templates;
- issue and PR templates for proposals and impact review;
- deterministic validation for mechanical invariants.

Potential checks include required attribution, status and provenance fields, unique canon IDs, relative links, required indexes, visible escaped newlines, and source-archive modification warnings. Do not claim these checks validate originality, sensitivity, creative quality, or authorial intent.

Use the installed **Manage Coding-Agent Harness** skill for substantial harness architecture, precedence, platform adapters, or enforcement. Preserve this skill's domain rules for canon, provenance, source material, and creative revision.

## GitHub readiness and delivery

GitHub is conditional. Before a write, follow the repository readiness guide and confirm identity, authorization, repository, owner, visibility, permissions, actual default branch, applicable instructions, and confidentiality compatibility.

Repository creation, visibility, initialization, publication, and merging are separate decisions. An empty repository needs a first commit before a normal branch can exist. Never bypass protected or instruction-governed workflows.

When requested and installed, use **GitHub Issue to Draft PR** for the issue, branch, approval, implementation, validation, commit, and draft-PR lifecycle. Creative approval to accept canon is distinct from approval to write repository files.

## Revision transaction

For an accepted change:

1. identify the decision and approving authority;
2. locate direct and downstream dependencies;
3. preserve the prior source and deliberate ambiguity;
4. update affected modular entries;
5. update the canon register and contradiction or open-question record;
6. update the attribution-aware change history;
7. validate navigation, identifiers, status, provenance, and scope;
8. report what remains proposed, disputed, unknown, or deprecated.

## Completion criteria

Complete repository-backed work only when attribution is visible, originals remain distinguishable, accepted canon and proposals are separated, relevant dependencies were reconciled, applicable harness rules are present, mechanical checks are reported honestly, and the user has a clear next creative move.
